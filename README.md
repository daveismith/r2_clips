# r2_clips

LED clips for the dome's WS2812B displays, pulled by the `r2_domeplayer` firmware with
`leds pull`. Nothing is pushed to the droid: it fetches this repo's `manifest.txt` and the
clips it lists, installs the ones that changed into `/data/clips`, and never deletes one.

## What is here

Each file is one clip in the `.r2lc` format, named `<name>.<target>.r2lc`. The target is the
grid it plays on:

| target | surface | grid |
| --- | --- | --- |
| `fld` | the two front logic boards as one | 8 x 10 |
| `rld` | the rear logic | 24 x 4 |
| `psi` | either PSI | 5 x 7 |

`leds run <surface> <name>` plays the clip of that name for the surface's target, so one name
usually has a file per target. The format is specified in r2_domeplayer's
`components/ws2812b/docs/effects_plan.md`.

`manifest.txt` lists every clip with its size and CRC-32. It is written from the files, never
by hand.

## Adding or changing a clip

With r2_domeplayer checked out beside this repo:

```sh
PY=~/.espressif/tools/python/v6.1/venv/bin/python
T=../r2_domeplayer/tools/led_clip.py

$PY ../r2_domeplayer/tools/led_clip_library.py .                # regenerate the whole set, and the manifest
$PY $T make pulse -t rld -o pulse.rld.r2lc                      # one generated clip
$PY $T convert rec.dat -t psi -o rec.psi.r2lc                   # a Glediator recording
$PY $T convert top.dat bottom.dat -t fld --fps 30 -o rec.fld.r2lc   # both front boards
$PY $T preview rec.psi.r2lc                                     # watch it through the maps
$PY $T info *.r2lc                                              # check what the board would say
$PY $T manifest .                                               # then rewrite manifest.txt
```

Commit the clips and the manifest together, then tag the set:

```sh
git tag v2 && git push origin main v2
```

## Pulling onto the droid

Pin a tag rather than a branch. A tag makes a pull reproducible, and it avoids
`raw.githubusercontent.com` serving a half-updated set from its cache of a branch:

```
esp32s3> leds pull -n https://raw.githubusercontent.com/daveismith/r2_clips/v1/
esp32s3> leds pull https://raw.githubusercontent.com/daveismith/r2_clips/v1/
```

`-n` reports what would change and downloads nothing. A pull reports every clip as new,
updated, same, not in manifest (kept) or failed. `leds clip rm <name>` is the only way a clip
leaves the board.

For development, serve a folder from the Mac over the USB link instead:

```sh
python3 -m http.server 8000 --bind 10.0.0.1      # in the folder
```

```
esp32s3> leds pull http://10.0.0.1:8000/
```

## Clips here

Every clip here is generated by r2_domeplayer's `tools/led_clip_library.py`, for all three
targets. Nothing is drawn by hand: to change a look, change its function and regenerate. The
output is deterministic, so an unchanged clip keeps its bytes and a pull skips it.

| clip | what it does | time at speed 5 |
| --- | --- | --- |
| `flash` | the colour on, then off | 200 ms each |
| `pulse` | the colour up and down in 32 steps each way | 2.56 s |
| `flipflop` | top half and bottom half trade full and 50/255 brightness | 200 ms each |
| `flipflop-alt` | the same split the other way: 8-wide blocks on the rear logic, left against right elsewhere | 200 ms each |
| `colourswap` | the colour, then its complement | 350 ms each |
| `alarm` | the colour, then red | 250 ms each |
| `alarm-twinkle` | the alarm's rhythm with every cell twinkling | a 4 s loop |
| `hscan` | a column of the colour sweeping left to right and back | 50 ms a step |
| `vscan` | a row of the colour sweeping top to bottom and back | 50 ms a step |
| `march` | halves (thirds on the rear logic) trading places on the beat, a new hue each segment | 48.3 s, once |
| `failure` | the display's own pattern racing, its hues turning, a fade to black, then dark | 18 s, once |

All but `march` and `failure` are tinted: they take the colour given to `leds run ... -c
rrggbb`, and a blue when none is given. `march` has its own hue per segment, and `failure`
the display's own colours; one PSI clip serves both PSIs, and takes the front PSI's.

The firmware carries `flash` and `pulse` built in; a pulled copy replaces the built-in one.

### Where the timings come from

The cadences are those of the classic logic display effects as Reeltwo
(github.com/reeltwo/Reeltwo, `src/dome/LogicEngine.h`) runs them at its default speed. Two
follow soundtracks, and their times are the recordings' as Reeltwo documents them:

- `march`: the Imperial March, the non-beep recording from the Padawan sound archive, which
  opens with 500 ms of silence. Segments start at 0, 9.8, 14.5, 19.3, 28.8, 38.3 and 45.3 s,
  and it ends at 48.3 s. The beat is 108 a minute; the last segment flips every 175 ms.
- `failure`: "128 screa-3.mp3". The scream to 1.8 s, the glitch to 6 s, a fade to black by
  8 s, and dark until 18 s. The dark tail is deliberate: a failed droid should not snap back
  to its idle drift the moment the fade ends. A run's duration can cut it short.

Reeltwo is LGPL-2.1 and nothing is ported from it: these are facts about the soundtracks and
how the effects look, and the generators are our own. Both clips line up with their sound
only if the run and the audio start together.
